# O que mudou no repositório (20/11/2026) e por quê

## 1. O fork foi atualizado para o firmware unificado do colega

**Antes (início do dia):** este fork tinha a versão antiga, com um projeto
PlatformIO separado por placa (`ares-firmware-esp1`, `ares-firmware-esp2`,
`tests/test-server`) e o `ingress_handler.py`.

**Agora:** o fork tem o mesmo conteúdo do repositório do colega
([dorneles-laboratory/ares.system](https://github.com/dorneles-laboratory/ares.system),
commit `b1735cf`), com o histórico dele preservado:

- **Um firmware só** para todas as placas, na raiz (`src/`, `include/`,
  `platformio.ini`, ambiente `ares_node`, ArduinoJson 7).
- O **papel** (GATEWAY, ROUTER, RELAY, STORAGE, MULE) é escolhido com o comando
  serial `role <n>` e fica salvo na memória da placa (NVS). Segurar o BOOT por
  0,5 s transforma a placa em GATEWAY.
- O **código antigo** não se perdeu: o colega moveu ele para `legacy/`.

**Por quê:** foi esse código que usamos no teste, e o fork precisava ficar igual
para dar para repetir e mostrar. A `main` antiga foi guardada na branch `main-antiga`.

## 2. Mudanças que fizemos no firmware do colega

Estão marcadas no código com `[CORRECAO USB]` e `[CORRECAO CANAL]`. São só 2 arquivos.

### `include/ares_config.h`

| Antes | Depois | Por quê |
| :--- | :--- | :--- |
| `ARES_ESP_NOW_CHANNEL 1` | `ARES_ESP_NOW_CHANNEL 11` | O Gateway fica no canal da rede Wi-Fi da base. O hotspot do Windows copia o canal da rede em que o notebook está (no teste, o Wi-Fi do celular, canal **11**). Com o canal 1, as placas não se ouviam. |

### `src/main.cpp`

| Antes | Depois | Por quê |
| :--- | :--- | :--- |
| Relay/Storage não escolhiam canal (ficavam sempre no 1) | `esp_wifi_set_channel(ARES_ESP_NOW_CHANNEL, ...)` no modo Relay/Storage (+ `#include <esp_wifi.h>`) | Sem isso, mudar o canal no `ares_config.h` só afetava a Router, e as Relay/Storage continuavam no 1. |
| `WiFi.setTxPower(WIFI_POWER_15dBm)` (3 lugares) | `WIFI_POWER_8_5dBm` | Menos pico de corrente quando o Wi-Fi liga. Na USB do notebook, o pico derrubava a tensão e a placa reiniciava (ou o USB caía e voltava). Na bancada o alcance continua de sobra. |
| `setCpuFrequencyMhz(80)` em Relay/Storage e `(160)` nos outros | comentado (CPU na velocidade padrão) | Deixar igual ao exemplo WiFiScan, que rodava estável na placa da Júlia. Uma coisa a menos mudando durante o boot. |
| `WRITE_PERI_REG(RTC_CNTL_BROWN_OUT_REG, 0)` (detector de brownout desligado) | **sem mudança** (continua desligado) | Testamos ligar o detector: a placa entrava em loop de `Brownout detector was triggered` assim que o Wi-Fi ligava. Desligado (como o colega fez), ela aguenta a queda. |

## 4. README da raiz

A seção **"Como Gravar"** mandava usar `pio run -d firmware/ares-mesh-node -e esp1_edge_sos ...`,
mas essa pasta e esses ambientes não existem no código. Trocamos pelos comandos
que funcionam (`pio run -t upload` + `role <n>` no monitor). O resto do README do
colega ficou como estava.

## Observação sobre as placas físicas

Durante o teste, algumas placas foram gravadas com uma versão intermediária
(detector de brownout **ligado**). A Router (`ESP32_599644`) e a Storage
(`ESP32_CBBC8C`) já estão com a versão final deste repositório. Se o Gateway ou as
Relay começarem a reiniciar com `Brownout detector was triggered`, é só regravar
com `pio run -t upload`. O papel salvo na placa continua.
